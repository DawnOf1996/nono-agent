# 设计取舍

> 前几页讲"是什么、怎么做"。这一页讲**"为什么不是另一种做法"**——
> 每个决定背后，都有一次在"简单 vs 完整"之间的权衡。

---

## 0. 一句话总纲

> **优先把"状态可复现"和"默认安全"做实，其余能力尽量做成可插拔。**

这句话拆开来就是本项目所有设计选择的来由。下面按重要性排列。

---

## 1. 会话日志：消息副本 vs 事件溯源

### 问题
Agent 每轮都在改一个消息数组。程序崩了想恢复、用户想反悔、想复盘"当时到底发生了什么"——
都要这个数组。但数组是**可变对象**，谁都能改。

传统做法：跑完一步就把消息数组追加进日志当快照。问题是——
**快照只能证明"我记下了什么"，不能证明"模型真的看到了什么"。**
中间只要有一处绕过日志改了数组，日志和现实就分叉了，而你不会知道。

### 选择
**落盘只有事件，消息数组由事件推导。**

```
引擎只 append 事件
      ↓
TranscriptWriter（协议）
      ↓
resume / fork / 回放：read_events() → derive_messages()
```

模型可见的任何东西（消息、工具调用、压缩边界、权限拒绝、记忆读写）
都先变成 `SessionEvent`；`derive_messages()` 是**纯函数**，同样的事件流永远推出同样的消息数组。

### 代价
- 每次请求前要重建一次上下文（可关闭：`session_invariant="off"`）。
- 写事件的调用点变多。
- 事件流比消息数组冗长。

### 收获
一次落盘，白送五件事：**可恢复、可分叉、可传输、可调试、可回放**。
再加上那条铁律——

> **模型可见 ⟺ 日志化。** 每次 LLM 请求前校验"事件流重建 == 运行时会话状态"，
> 不一致就终止本轮。

这条门禁把"偷偷改上下文"这类隐性 bug 从"难查"变成"不可能"。详见
[会话可观测性](../architecture/session-observability.md)。

### 一个衍生的有意思的点

事件流要覆盖所有改变上下文的路径，就得回答"**谁有资格写事件**"。
答案不是"引擎统一写"，而是**按信息所在位置分三处**：

| 发射者 | 它才知道的 |
|--------|-----------|
| `QueryEngine` | 循环吐出来的消息（assistant/tool/usage） |
| `agentic_loop` | 循环内部状态（step 边界、重试次数、`store.replace()`） |
| 工具 / 记忆 | 工具内部发生的事（权限拒绝、记忆读写） |

工具被权限拦下来，引擎和循环都只看到"工具返回了一个错误"——
只有工具自己（或它的拒绝追踪器）知道真正发生了什么。所以发射权必须跟着信息走。

## 2. 安全默认：fail-closed vs 方便优先

### 问题
工具说"我能不能并发执行""我有没有写副作用"，答错的后果不对称：
- 答"能并发"但其实不能 → 数据竞争、文件写坏，**很难查**。
- 答"不能并发"但其实能 → 只是慢一点，**用户看不出来**。

### 选择
**默认值一律倒向保守，fail-closed。**

| 维度 | 默认值 | 含义 |
|------|--------|------|
| `is_concurrent_safe` | `False` | 忘声明 → 串行 |
| `has_write_side_effects` | `True` | 忘声明 → 权限先问 |
| 权限模式 | `default` | 写操作先确认 |
| 非法配置 | 降级到 `default` | 而不是放行 |

连 `bypass` 模式下显式 `DENY` 规则都依然生效——"全放行"不等于"无视禁令"。

### 代价
新手要显式声明每个工具的两个布尔，否则一切串行、什么都要问。有点烦。

### 收获
**忘声明的后果是慢，不是危险。** 这个方向的代价不对称是值得的。

## 3. 工具调用：并行还是串行

### 问题
模型一轮可能返回 3 个工具调用。串行简单但慢，并行快但可能撞。

### 选择
**按工具自身的"并发安全性"决定，能并行的并行，其余串行。**

```
read_file(a) ┐
read_file(b) ├─ 都声明了并发安全 → 并行
grep("foo")  ┘
edit_file(a)     ┐
bash("pytest")  ┴─ 未声明        → 并行组跑完后，串行保序
```

> 注意判据**只有** `is_concurrent_safe` 一个。
> `has_write_side_effects` 不参与调度——它只喂给权限（要不要问你）。
> 所以两者会交叉：`job_kill` 既并发安全又有写副作用（走并行组），
> `lsp` 无写副作用但没声明并发安全（走串行组）。

### 值得学的接缝：Shell 不让工具直接 spawn 进程

工具不 `subprocess.run`，而是构造一个 `ShellSpec`（描述"执行什么"），
交给可替换的 `ShellExecutor`。于是超时分类、进程组终止、输出收集、游标语义
全部集中在执行器，工具只管描述和渲染。

将来接沙箱执行器只需覆写构造 argv 的部分。**这就是把"描述"和"执行"分成两层的价值。**

### 一个反直觉的正确做法

命令**超时不杀进程，而是晋升为后台作业**继续跑，返回 job id 让模型用 `job_output` 跟进。
理由：Agent 跑的命令经常是 `npm install`、长测试——杀掉反而浪费，
不如让它跑完、模型自己决定还要不要等。

配套的坑也处理得很细：终止要杀**整个进程组**。
只杀 shell 的话，shell 启动的孙进程会继续持有输出管道，调用方会被拖到它自然结束。

详见 [Shell 工具](../architecture/shell-tool.md)。

## 4. 配置：单层快照 vs 分层合并

### 问题
两种配置需求打架：
- **运行期门控**要求配置在一轮内是**冻结的快照**（否则循环中途变了就没法复现）。
- **用户定制**要求配置分散在多层（默认/用户/项目/策略/命令行）。

### 选择
**分成两套，各管一件事。**

| | `EngineConfig` | `Settings` |
|---|---------------|------------|
| 形态 | `frozen=True` Pydantic | 五层 JSON 合并 |
| 生命周期 | 构造引擎时设定 | 启动时合并 |
| 读法 | 引擎直接持有 | `Settings.get("permissions.mode")`（点分路径） |
| 用途 | 冻结的运行参数 | 用户可改的定制点 |

五层优先级：`default < user < project < policy < flag/env`。

### 为什么单靠 `EngineConfig` 不够
它没法表达"用户配置和项目配置怎么合并"。为什么单靠 `Settings` 不够
——它没法在一次循环里保证值不变。

### 一个细节值得学
`Settings` 记录每个叶子键的**来源层**，所以 `source_of("permissions.mode")` 能告诉你
这个值到底是 `project` 还是 `user` 设的。排查"我的配置为什么没生效"时非常有用。

## 5. 状态机：裸字段 vs 显式状态

### 问题
Agent 会继续也会停止，但"为什么"如果不记，出问题时你只知道"它停了"，不知道"为什么停"。

### 选择
**继续和终止都是显式枚举，每次循环必须二选一。**

- `TransitionReason`（7 种）：为什么还要转下一轮
- `TerminalReason`（11 种）：为什么结束
- `LoopState` 是 `frozen` dataclass，继续时构造新实例

### 好处不只是"好读"
`frozen=True` 让"跑到一半就地改状态"不可能发生——每次转移都是一次完整的构造调用，
而循环里只有 6 个这样的构造点，于是**所有状态转移是一份可 grep 的清单**。

> 严谨地说：它防的是**就地改**，不防**漏传字段**（漏传会静默取默认值）。
> 这 6 个构造点之间也不完全一致——正常 `NEXT_TURN`（`loop.py:720`）会重置恢复计数并递增
> `turn_count`，而四条恢复路径（`857/878/902/924`）都**省略了 `auto_compact_tracking`**，
> 于是它回落成 `None`；其中 `924` 也会递增 `turn_count`，另外三条则保持不变。
> 所以漏传字段这件事靠的是 review 和测试，不是 `frozen`。

> 已订正的一处笔误：`state.py` 顶部注释原写"10 种终止原因"，实际枚举是 **11 个**——
> 源码注释已同步改正，文档以代码为准。

## 6. 错误处理：内联处理 vs 决策集中

### 问题
API 错误种类多（`prompt_too_long`、`max_output_tokens`、`media_size`、`model_error`……），
每种的恢复动作还不一样。散在循环里写会乱。

### 选择
**用一个 `RecoveryChain` 集中决策，用 `match/case` 穷举错误类型。**

策略按优先级递进，例如 `max_output_tokens`：
先升级 `max_tokens` 到 64k → 还不够则注入"请继续输出"（上限 3 次）→ 再不行才终止。

### 好处
所有恢复逻辑集中在一处，加新错误类型只改一个 `match`。而且编译器/检查器
能在你漏掉某个 case 时提醒。

## 7. 上下文压缩：一个大策略 vs 分级阶梯

### 问题
上下文窗口有限。压缩有代价（丢信息），能晚压就晚压。

### 选择
**分级阶梯，默认 4 级，按窗口百分比触发：**

```
ToolResultBudget → SnipCompact → MicroCompact → AutoCompact
（可选）ContextCollapse：调模型做摘要式折叠
```

- `ToolResultBudget`：先压超长工具输出（最容易膨胀、损失最小）
- `SnipCompact`：滑动窗口丢弃
- `MicroCompact`：剥离 thinking 并截断
- `AutoCompact`：80%/95% 安全网

### 思路
**先用便宜的、对内容破坏小的手段，实在不行再用贵的。**
最贵的 `ContextCollapse` 要额外调一次模型，所以默认不启用。

### 一个精妙的细节：估算偏低时的兜底
token 估算对工具 JSON schema 普遍偏低（实测差约 40%）。所以
`effective_tokens = max(估算值, provider 实测下界)`——否则真超窗了压缩还没触发。

详见 [上下文压缩](../architecture/context-compression.md)。

## 8. 扩展：继承体系 vs 声明式清单

### 问题
用户想让引擎多一个工具/插件，走哪条路？

### 选择
**分两种粒度，都不走 Python 代码扩展：**

| 粒度 | 机制 | 例子 |
|------|------|------|
| 打包下层能力 | `plugins/`（`plugin.json` 组合 rules/skills/agents/mcp） | 一个"团队规范包" |
| 直接变成工具 | `toolplugins/`（`http_json` / `mcp` 声明式） | "开开关+填 Key = 一个搜索工具" |

**关键：清单不含可执行代码路径。** 所以引擎不必给插件开 Python 导入的口子。
这既是**安全边界**（插件不能在引擎里执行任意代码），也是**分发优势**（丢个目录就生效，不用装包）。

### 代价
复杂逻辑写不进插件。真正复杂的工具还是得写成 Python 实现 `Tool` 协议再注册。

## 9. 子 Agent：共享上下文 vs 独立上下文

### 问题
派一个子 Agent 去做子任务时，它该看到多少主对话？

### 选择
**给子 Agent 一套全新的隔离上下文。**

- 新的 `session_id`（不是父的）
- 新的工具注册表（按定义裁剪）
- **不注册 `agent` 工具**——从结构上防止子 Agent 再派子 Agent，防止无界嵌套

### 理由
子任务是"查清某个文件"这种专注活，不需要背着主对话的几十轮历史。
隔离既省 token（不会把主对话全塞进去），又防止递归失控。

## 10. 可观测性：各自埋点 vs 事件流投影

### 问题
"这一轮慢在哪、哪一步最贵"这类问题，要有指标才能回答。

### 选择
**事件流是唯一真源，指标是它的聚合投影。**

每条事件自动计入 `session.events`，关键事件另计入
`session.turns`/`session.steps`/`tool.executions`/`api.errors`/`compact.operations`/
`permission.denials`/`memory.write`/`memory.retrieve`，
标签统一用 `session_id` 加上 `event`/`reason`/`tool`/`kind` 之一
（投影里目前没有 `model` 标签，尽管 `TAG_MODEL` 常量已定义）。

### 好处
只有一条真源，不会出现"日志里有、指标里没有"。且两者主键天然对齐——
从指标能回跳到事件，从事件能聚合到指标。

**注意**：脱敏不在 `observability/`，而在 `session/redact.py`（读取/导出侧）。
落盘保持逐字真实，否则事件流就不再等于"模型真的看到了什么"。

## 11. 一条贯穿的元决策

回看上面每一个取舍，几乎都遵循同一条元原则：

> **让"忘配"和"忘了声明"的后果，变成安全的那一边。**

- 忘声明并发安全 → 串行（慢，不危险）
- 忘声明写副作用 → 先问（烦，不危险）
- 非法配置 → 降级到默认（不危险）
- 忘了记事件 → 门禁拦住（吵闹，但不会静默出错）
- 上下文真超窗了 → 也有 provider 实测下界兜底

这比"假设用户都会正确配置"更耐用。
